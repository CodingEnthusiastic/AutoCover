% ABSTRACT

\begin{abstract}

Vehicle insurance comparison often requires customers to navigate
multiple portals, repeatedly enter vehicle information, and interpret
inconsistent coverage terminology and pricing structures.

\textbf{AutoCover} addresses this problem through an end-to-end car
insurance aggregation, comparison, and policy lifecycle platform.

Built using \textbf{React 18}, \textbf{TypeScript}, \textbf{Python 3.12},
\textbf{FastAPI}, and \textbf{SQLAlchemy}, the application accepts a
vehicle registration number and aggregates quotes from four simulated
insurance providers. Each provider represents a different data source:
a JSON REST API, a JavaScript-hydrated HTML page, a PDF tariff rate card,
and a CSV export.

The platform implements provider-specific parsing, duplicate detection,
malformed-data handling, premium and GST normalization, canonical
add-on mapping, multi-dimensional plan scoring, and asynchronous
aggregation. It also provides vehicle verification, policy record
management, and renewal tracking.

This report documents the system architecture, provider integration
strategies, data normalization methodology, recommendation engine,
database structure, automated testing, and local execution procedure.

\end{abstract}

\section{Executive Summary}

AutoCover simplifies the vehicle insurance discovery process through
a unified comparison and policy management workflow.

Instead of requiring customers to visit multiple provider interfaces,
the platform collects and standardizes quote information through a
single vehicle lookup.

The major capabilities are summarized below.

\begin{enumerate}

    \item \textbf{Single-Entry Vehicle Lookup}

    Customers enter their vehicle registration number once.
    AutoCover normalizes registration formats, retrieves vehicle
    specifications from its vehicle registry, and allows manual
    verification or overrides when the registered information differs
    from the vehicle's Registration Certificate (RC).

    \item \textbf{Concurrent Multi-Provider Aggregation}

    The backend communicates with four simulated providers concurrently.
    Provider B introduces approximately 1.5 seconds of simulated latency,
    while Provider D can return intermittent HTTP 503 responses.
    Provider failures are isolated so that available responses from
    other providers can still be processed.

    \item \textbf{Heterogeneous Data Ingestion}

    Each provider uses a different data representation.
    AutoCover handles JSON, hydrated HTML, PDF-based tariff calculations,
    and CSV exports through dedicated parsing and processing logic.

    \item \textbf{Canonical Add-on Normalization}

    Provider-specific marketing terminology is mapped into a common
    add-on taxonomy, allowing customers to compare equivalent coverage
    concepts across providers.

    \item \textbf{Transparent Value Scoring}

    Plans are evaluated using price affordability, Insured Declared Value
    (IDV), add-on protection depth, and quote validity.

    \item \textbf{Policy Lifecycle Management}

    Selected policies are persisted in the database with vehicle,
    customer, premium, coverage, and expiry details. The system supports
    policy tracking and simulated renewal reminder workflows.

\end{enumerate}

\begin{infobox}[title={Core Engineering Objective}]
AutoCover demonstrates how heterogeneous insurance quote sources
can be transformed into a unified comparison experience using
provider-specific parsers, asynchronous aggregation, canonical
normalization, and transparent recommendation logic.
\end{infobox}

\section{High-Level System Architecture}

\subsection{Architecture Overview}

AutoCover separates the customer-facing interface, API layer,
aggregation engine, provider-specific integrations, normalization
services, and persistence layer.

The major processing sequence is:

\begin{enumerate}
    \item The customer enters a vehicle registration number.
    \item The React frontend sends the lookup request to FastAPI.
    \item The backend retrieves the vehicle profile and relevant
    vehicle details.
    \item The asynchronous aggregator dispatches requests to the
    four simulated providers.
    \item Provider-specific drivers parse the returned data.
    \item The normalization layer standardizes premiums, IDV,
    validity, and add-on terminology.
    \item The ranking engine computes value scores and recommendation
    badges.
    \item The frontend receives a unified comparison response.
    \item Selected policies can be persisted for lifecycle tracking.
\end{enumerate}

\subsection{Provider A: JSON REST API}

\textbf{Source File:} \texttt{provider\_a.json}

Provider A exposes quote information through a structured JSON
representation.

The implementation handles the following cases:

\begin{itemize}

    \item \textbf{Duplicate Quote Detection:}
    Duplicate quote records are identified using a composite
    key containing plan, coverage, IDV, premium, and add-ons.

    For example, duplicate quote entries for
    \texttt{WB02AB1234} are detected and consolidated.

    \item \textbf{Premium Tax Isolation:}
    Some records contain a base premium with a separate tax structure,
    while others provide an inclusive premium with a
    \texttt{premium\_includes\_gst} indicator.

    These representations are normalized into a common
    base-premium and GST structure.

    \item \textbf{Quote Validity:}
    Quote expiry dates are evaluated against the configured
    reference date of 10 November 2026.

    \item \textbf{Underwriting Declines:}
    Declined quotes are preserved with their rejection reasons
    instead of being silently discarded.

\end{itemize}

For example, vehicle \texttt{WB06CD5678} has an underwriting
decline associated with vehicle age exceeding ten years.

% ------------------------------------------------------------
% PROVIDER B
% ------------------------------------------------------------

\subsection{Provider B: HTML with JavaScript Hydration}

\textbf{Source File:} \texttt{provider\_b.html}

Provider B represents a common modern web integration challenge:
the static HTML contains the structure of the quote cards, but
the actual pricing information is populated through JavaScript.

An example of the embedded state is:

\begin{lstlisting}[language=javascript,caption={Example of Provider B hydrated quote data}]
window.__QUOTE_DATA__ = {
    "B-101": {
        "total": "INR 12,830",
        "cover": "3.1 L",
        "valid_till": "30-11-2026"
    }
};
\end{lstlisting}

The extraction process follows these steps:

\begin{enumerate}

    \item Parse the HTML document and identify the quote cards
    using BeautifulSoup.

    \item Extract the embedded
    \texttt{window.\_\_QUOTE\_DATA\_\_} JavaScript state.

    \item Decode the JSON data stored within the script.

    \item Match the extracted pricing and coverage information
    with the corresponding HTML quote cards.

    \item Convert Lakhs-formatted IDV values into integer
    Rupee values.

\end{enumerate}

For example:

\begin{center}
\begin{tabular}{@{}ll@{}}
\toprule
\textbf{Input Representation} & \textbf{Normalized Value} \\
\midrule
\texttt{3.1 L} & ₹3,10,000 \\
\texttt{12.5 L} & ₹12,50,000 \\
\bottomrule
\end{tabular}
\end{center}

A simulated delay of approximately 1.5 seconds is introduced
to represent a slower external provider.

\subsection{Provider C: PDF Tariff Rate Card}

\textbf{Source File:} \texttt{provider\_c.pdf}

Unlike the other providers, Provider C does not simply return
pre-existing static quotes. It supplies tariff information that
is used by the backend to calculate quotes dynamically.

The calculation follows the documented tariff structure.

\subsubsection{Insured Declared Value Calculation}

The basic IDV calculation is:

\[
\boxed{
\text{IDV}
=
\text{Ex-Showroom Price}
\times
(1-\text{Depreciation})
}
\]

The depreciation percentage depends on the vehicle's age.

3 to 4 years & 40\% \\
4 to 5 years & 50\% \\
5 to 8 years & 50\% + 5\% per additional year after 5 years \\

% ============================================================

\section{Assumptions and Business Rules}

The application uses the following documented assumptions
for quote evaluation and demonstration scenarios.

\begin{enumerate}

    \item \textbf{Reference Date}

    Quote validity and expiry calculations use
    \textbf{10 November 2026 (IST)} as the reference date.
    This value is configurable through the
    \texttt{REFERENCE\_DATE} environment variable.

    \item \textbf{GST}

    The application applies an 18\% GST assumption and
    displays GST separately from the net base premium.

    \item \textbf{Registration Number Normalization}

    Spaces, hyphens, and letter casing are ignored when
    comparing registration numbers.

    For example:

    \[
    \texttt{wb 02 ab 1234}
    \longrightarrow
    \texttt{WB02AB1234}
    \]

    \item \textbf{Vehicle Registry Fallback}

    When a registration number is unavailable in
    \texttt{registry.json}, the application provides a
    draft vehicle profile rather than immediately
    rejecting the lookup.

    \item \textbf{Provider C Depreciation}

    Provider C follows the documented depreciation tiers,
    with IDV rounded to the nearest ₹1,000 and premiums
    rounded to the nearest rupee.

    \item \textbf{Underwriting Eligibility}

    Provider C declines vehicles older than eight years.

\end{enumerate}

\begin{warningbox}[title={Simulation Scope}]
The four provider integrations represent simulated data sources
for engineering evaluation. Provider latency and HTTP 503 failures
are intentionally simulated. Renewal notifications are also
simulated workflows rather than evidence of live insurer or
messaging-service integrations.
\end{warningbox}

pip install -r requirements.txt

python -m pytest -v

\section{Conclusion}

AutoCover demonstrates an end-to-end approach to consolidating
vehicle insurance information from multiple heterogeneous sources
into a unified comparison and policy management experience.

The project brings together several practical full-stack
engineering concepts:

\begin{itemize}

    \item Development of a typed React frontend and REST-based
    Python backend.

    \item Integration of multiple data formats through
    provider-specific parsing strategies.

    \item Handling of duplicate, expired, malformed, and
    incomplete quote records.

    \item Asynchronous request orchestration and isolation
    of simulated provider failures.

    \item Standardization of insurance add-ons through a
    reusable canonical terminology layer.

    \item Multi-factor plan scoring instead of relying
    exclusively on the lowest premium.

    \item Persistent policy management using SQLAlchemy ORM
    with SQLite and PostgreSQL configuration support.

    \item Automated testing across API endpoints, parsing,
    business services, and complete aggregation flows.

\end{itemize}

The resulting platform provides a structured foundation for
insurance quote comparison, demonstrates practical handling
of inconsistent external data, and establishes an extensible
architecture for additional provider integrations.
